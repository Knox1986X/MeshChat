# Безопасность

Честный документ: что MeshChat защищает, чего не защищает и где границы.

## Модель угроз

**Активы:** текст переписки, файлы, список контактов, долгосрочные ключи.

**Кто может атаковать:**

| Противник | Возможности | Что видит / может |
|---|---|---|
| Владелец relay | всё, что хранится и логируется | теги, размеры, время, IP подключений (если включён лог) |
| Хостер / провайдер | трафик, доступ к диску | TLS-метаданные, объём трафика |
| Владелец git-репозитория | содержимое репозитория и история коммитов | конверты, теги, время коммитов |
| Пассивный наблюдатель | трафик | IP, время, размеры |
| Активный MITM | подмена ответов сервера | может подсунуть чужой prekey bundle |
| Локальный доступ к устройству | файлы браузера | IndexedDB с историей |

**Вне модели:** компрометация самого браузера/ОС, кейлоггеры, скриншоты,
собеседник-предатель, глобальная корреляция трафика на уровне государства.

## Криптография

| Задача | Примитив | Параметры |
|---|---|---|
| личность, подписи | Ed25519 | libsodium, 32-байтовый seed |
| согласование ключа | X25519 (конверсия из Ed25519) | X3DH, 3–4 DH |
| шифрование сообщений | XChaCha20-Poly1305 IETF | 256-бит ключ, 192-бит nonce |
| KDF | HKDF-SHA256, HMAC-SHA256 | — |
| хеши, теги, PoW | BLAKE2b-256 | — |
| бэкап личности | Argon2id + XChaCha20 | 64 MiB, 3 итерации |
| RNG | `crypto.randombytes_buf` (libsodium) | — |

Всё в одном модуле: `packages/core/src/sodium.ts`. Других криптографических
вызовов в проекте нет — это упрощает аудит.

### Свойства

* **Forward secrecy.** Ключ каждого сообщения выводится из цепочки и стирается
  после использования; старые сообщения нельзя расшифровать, узнав текущий ключ.
* **Post-compromise security.** Каждый ответ собеседника делает DH-ratchet:
  после утечки состояния сессии связь восстанавливается.
* **Аутентификация.** SPK подписан Ed25519; bundle проверяется против ключа из
  приглашения. Подмена relay'ем приводит к отказу, а не к «тихому» MITM.
* **Анонимность отправителя.** Обычный конверт не содержит `from`; получатель
  подбирает сессию сам. Relay видит только тег получателя.
* **Анти-спам без аккаунтов.** PoW-сложность задаёт сервер; клиент уважает её
  (`settings.powDifficulty = 0` → авто).
* **Устойчивость к подделке тега.** Сервер не отдаёт prekeys, если `ik`
  отличается от ранее опубликованного для этого тега.

### Реализация: на что смотреть при аудите

1. `ratchet.ts` — порядок DH-шага, обработка skipped-ключей, привязка заголовка
   как associated data.
2. `engine.ts` — копирование состояния сессии перед попыткой расшифровки
   (иначе неудачный кандидат продвинет цепочку), дедупликация, отбрасывание
   конвертов с чужим тегом.
3. `relay/src/server.ts` — проверка PoW до записи, лимиты размера/количества,
   отсутствие логирования содержимого.

## Что НЕ защищено

1. **Метаданные.** Relay знает: тег получателя, момент, размер, примерный объём
   переписки. Он не знает отправителя, но при одном активном пользователе
   корреляция тривиальна. Митигации: свой relay, Tor, несколько relay,
   случайные задержки (roadmap).
2. **Локальная база.** IndexedDB не зашифрован паролем. Любой, кто получил доступ
   к профилю браузера, прочитает историю. Roadmap: passphrase-lock с Argon2id.
3. **Одно устройство на личность.** Синхронизации нет; при переустановке нужен
   бэкап ключа.
4. **Preamble в prekey-конверте.** Первое сообщение содержит `ik` инициатора в
   открытом виде (так устроен X3DH без sealed sender). Дальше — нет.
5. **Размер и тайминг.** Паддинг скрывает длину в пределах 256 байт, но не факт
   «человек печатает 10 минут» или «файл на 8 МБ».
6. **Git-транспорт** оставляет след: время коммитов, публичный репозиторий с
   тегами. Содержимое остаётся шифротекстом.
7. **Код не аудирован.** Это эксперимент, а не Signal.

## Практические рекомендации

* Сравните safety number вне мессенджера. Это единственная защита от MITM на
  этапе обмена ключами.
* Для действительно чувствительного — свой relay в Tor onion-сервисе, оба
  собеседника через Tor Browser.
* Отключите «отчёты о прочтении» и «печатает», если не хотите отдавать ритм
  общения.
* Ставьте исчезающие сообщения (1 ч) для всего, что не должно пережить день.
* Не используйте публичные relay для незаконного — это чужие серверы.
* Держите бэкап личности офлайн (бумага/менеджер паролей), парольную фразу — в
  голове.

## Границы доверия к серверу

Relay может: не доставлять, удалять, задерживать, подменять **публичные**
prekeys (но их проверяет подпись), собирать статистику, блокировать по IP.
Relay не может: расшифровать конверт, выдать себя за собеседника (нет приватного
ключа), изменить содержимое незаметно (AEAD).

Если relay недоступен — клиент пробует остальные транспорты и держит сообщения в
очереди 24 часа.

## Ответственное раскрытие

Нашли проблему? Откройте issue с меткой `security` **без** публичных деталей
эксплойта, либо напишите мейнтейнеру приватно. Мы подтвердим получение в течение
нескольких дней. Пожалуйста, не публикуйте PoC до исправления.

## Зависимости

* `libsodium-wrappers-sumo` — эталонная реализация NaCl/libsodium.
* `ws`, `react`, `qrcode` — не касаются секретов.
* Никаких внешних CDN, аналитики, шрифтов и «обёрток» вокруг криптографии.

Проверить дерево зависимостей:

```bash
npm audit
npm ls --all --omit=dev
```
