# Финальный чеклист безопасности MeshChat (ШАГ 5)

Документ фиксирует, какие защитные механизмы **реализованы в коде и подтверждены автотестами**, а какие угрозы **остаются за пределами MVP** и требуют внимания перед эксплуатацией в условиях целевых атак высокого уровня.

---

## 1. Что уже реализовано и проверено автотестами (`npm test` — 12/12)

### Анонимность и защита метаданных
- [x] **Нулевой сбор персональных данных при регистрации:** только `@username`, пароль (остаётся на клиенте) и сгенерированные в браузере публичные ключи; телефон, e-mail и OAuth не используются.
- [x] **Отсутствие реальных IP-адресов на диске и в логах (`server/privacy-gate.mjs`):** входящий IP мгновенно пропускается через `HMAC-SHA256(IP, ephemeralBootSalt)` исключительно для in-memory rate-limiting; соль живёт только в ОЗУ и ротируется каждые 6 часов. Проверено форензик-тестом дампа БД в `tests/server.test.mjs`.
- [x] **Слепая доставка сообщений Sealed Sender (`shared/crypto/sealed-sender.mjs`, `server/rpc.mjs`):** метод `relay.drop` авторизуется криптографическим доказательством `HMAC(mailboxWriteToken, sealedBytes)` без привязки к сессии отправителя. Внешний конверт зашифрован на одноразовом эфемерном ключе ECDH P-256 — сервер знает только обезличенный `mailboxId` получателя, но не знает, кто отправил конверт.
- [x] **Квантованный паддинг длины сообщений (`shared/crypto/primitives.mjs`):** все сообщения перед шифрованием дополняются по ISO/IEC 7816-4 до корзин кратного размера (`256 Б`, `512 Б`, `1 КБ`, `2 КБ`, `4 КБ`…), скрывая точную длину коротких фраз, реакций и уведомлений о наборе текста.
- [x] **Фоновый шумовой трафик (`COVER`, `shared/codec/binary-frame.mjs`):** опциональная отправка неотличимых по длине 512-байтных кадров `COVER` поверх TLS/Tor-соединения, которые сервер молча отбрасывает.
- [x] **Защита анонимных вопросов («Голая правда») без деанонимизации:** спам отсекается адаптивным клиентским Hashcash Proof-of-Work (`14–20 бит`), а блокировка тролля получателем работает по `HMAC-SHA256(clientTag, recipientAskSalt)` без раскрытия IP ни серверу, ни получателю.

### Криптография и хранение ключей
- [x] **Сквозное шифрование (E2E) по умолчанию для всех чатов и файлов:**
  - Установление сессии по схеме **Signal X3DH** (`IK + SPK + OPK`, с криптографической связкой ключей подписи и обмена `MSG-IK-BIND-v1` и детерминированным разрешением коллизии встречных рукопожатий).
  - Посообщенческая прямая секретность (Forward Secrecy) и самовосстановление после компрометации (Post-Compromise Security) за счёт **Double Ratchet** (симметричный KDF-ратчет + шаговый ECDH-ратчет с окном пропуска `MAX_SKIP = 256` и защитой от повтора).
  - Клиентское шифрование всех файлов до загрузки на сервер (`AES-256-GCM` со случайным 256-битным ключом + проверка целостности `SHA-256` до расшифровки).
- [x] **Zero-Knowledge аутентификация без хранения хешей паролей на сервере (`shared/crypto/kdf.mjs`, `server/auth.mjs`):**
  - Пароль растягивается на клиенте через **Argon2id** (`m = 64 МиБ, t = 3, p = 1`, WASM) с резервом на **scrypt** (`N = 2^17, r = 8, p = 1`).
  - Сервер хранит только публичный ключ `ECDSA P-256` и зашифрованный блоб; вход выполняется подписью одноразового `challengeNonce`.
  - **Защита от перебора существующих логинов (анти-энумерация):** для несуществующих аккаунтов сервер детерминированно синтезирует неотличимый по длине и энтропии криптоблоб от серверного секрета.
- [x] **Изоляция приватных ключей от XSS и дампа памяти браузера:**
  - Долгосрочные ключи хранятся в IndexedDB с атрибутом WebCrypto **`extractable: false`** (`public/js/crypto/keystore-idb.mjs`) — даже при выполнении скрипта атакующий не может экспортировать сырые байты приватного ключа.
  - Все криптооперации изолированы в выделенном **Web Worker (`crypto.worker.mjs`)**.
  - Локальная история чатов и очередь Outbox в IndexedDB шифруются неизвлекаемым ключом `AES-256-GCM` (`idb-messages.mjs`); **`localStorage` и `sessionStorage` не используются вовсе (`0 байт`)**.
- [x] **Сверка ключей (Safety Numbers):** детерминированный 60-значный цифровой код и 8 эмодзи (`5200` раундов `SHA-256`) для защиты от активного MITM при подмене ключей зловредным сервером.
- [x] **Одноразовые файлы (`once`) и исчезающие сообщения (TTL):** одноразовый шифроблоб затирается нулями в памяти и физически удаляется (`fs.unlink` + удаление из S3) в момент первого чтения по `x-veil-burn-token`.
- [x] **Эфемерный TURN:** вместо долгоживущих общих паролей генерируются одноразовые `HMAC-SHA1` учётные данные ровно на **5 минут**.

### Мультитранспорт и защита веб-оболочки
- [x] **Жёсткий Fail-Closed в режимах `TOR_ONLY` и `I2P_ONLY`:** `TransportRegistry` и `FallbackTransport` гарантированно блокируют прямой `WebSocketTransport` и `WebRTCTransport` (утечку IP через STUN); подтверждено тестом `tests/multitransport.test.mjs`.
- [x] **Отсутствие утечек DNS в SOCKS5-мосте (`tools/local-proxy-bridge.mjs`):** используется строго `ATYP = 0x03` (передача `.onion` / `.b32.i2p` имени внутрь Tor/i2pd без локального DNS-резолвинга ОС) и проверка `Origin`.
- [x] **Строгий CSP и защита DOM:** `default-src 'self'; object-src 'none'`; отсутствие `innerHTML` во всём UI (используется безопасный VDOM Preact); контейнер работает под непривилегированным пользователем `node` с `read_only: true` и `no-new-privileges`.

## 2. Что остаётся за рамками MVP (честные риски и план усиления перед High-Risk продакшеном)

1. **Глобальный пассивный наблюдатель и тайминг-корреляция трафика:**
   - *Статус в MVP:* есть квантованный паддинг размеров пакетов и периодические `COVER`-кадры, но отправка сообщений происходит в реальном времени (low-latency).
   - *Риск:* противник уровня крупного транзитного оператора (AS-level), контролирующий одновременно вход и выход или наблюдающий моменты активности обоих собеседников, может коррелировать всплески пакетов по времени.
   - *Как закрывать дальше:* добавить опциональный режим микснета с пуассоновскими задержками (Loopix/Nym-стиль, ценой задержки доставки 2–10 с).

2. **Прозрачность ключей (Key Transparency) при первом контакте (TOFU):**
   - *Статус в MVP:* безопасность первого обмена опирается на ручную сверку 8 эмодзи / 60 цифр по независимому каналу. Если пользователи не сверили код безопасности, скомпрометированный сервер теоретически может подменить `PreKeyBundle` при самом первом запросе.
   - *Как закрывать дальше:* внедрить неизменяемое дерево Меркла публичных ключей (аналог CONIKS / Signal Key Transparency) с перекрёстной проверкой корня дерева через пиров.

3. **Криптографическая схема для больших групп (> 8 человек):**
   - *Статус в MVP:* личные чаты используют полноценный Double Ratchet, малые P2P-комнаты до 8 участников — WebRTC Mesh с попарными ратчетами.
   - *Как закрывать дальше:* для групп на 50–1 000 участников реализовать протокол **Sender Keys** или **MLS (RFC 9420)**, чтобы сложность отправки была $O(1)$, а не $O(N)$.

4. **Постквантовая устойчивость (Harvest Now, Decrypt Later):**
   - *Статус в MVP:* используется классическая эллиптическая криптография NIST P-256 (`ECDH` + `ECDSA`) из стандартного браузерного WebCrypto API (ради нулевого веса и аппаратного ускорения).
   - *Как закрывать дальше:* перейти с чистого X3DH на гибридное рукопожатие **PQXDH** (`P-256 / X25519 + ML-KEM-768 / Kyber`) и добавить периодическое домешивание KEM-капсул в Double Ratchet (аналог Signal SPQR).

5. **Доверие к раздаче веб-клиента (Web App Code Integrity):**
   - *Статус в MVP:* Service Worker кеширует проверенную версию оболочки после первого визита, но при самой первой загрузке в браузере код отдаётся сервером. Злонамеренный администратор узла теоретически может отдать модифицированный JS конкретному пользователю.
   - *Как закрывать дальше:* упаковать клиентскую папку `public/` в воспроизводимую сборку браузерного расширения (Manifest V3 с подписью) и/или десктопный Tauri/Electron пакет с зашитым хешем бандла и Subresource Integrity (SRI).

6. **Независимый внешний криптоаудит и защита от боковых каналов на устройстве:**
   - *Статус в MVP:* используются стандартные примитивы WebCrypto API и `node:crypto`, но сама протокольная обвязка (`x3dh.mjs`, `double-ratchet.mjs`, `sealed-sender.mjs`) написана с нуля для этого проекта и не проходила платный сторонний аудит.
   - *Ограничение среды:* если само конечное устройство пользователя заражено трояном/кейлоггером на уровне ОС или вредоносным браузерным расширением с правами чтения всех вкладок, ни один протокол сквозного шифрования не защитит текст на экране.
